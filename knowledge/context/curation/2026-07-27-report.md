- **[CONTRADICTION]** `knowledge/context/authoring/view_dashboard_design_guide.md:318-329`
  ("Dashboard layout conventions" / "Grid system") vs `knowledge/context/defects.md`
  DEF-013 (closed) + its follow-up FB-017 (open). The design guide — required reading for
  any dashboard authoring — states: "`y`: row (0-based, grows downward)" and gives two
  worked examples using `y: 0` (`coords: {x: 1, y: 0, w: 4, h: 6}` at line 240;
  `coords: {x: 0, y: 0, w: 12, h: 4}` at line 323, captioned "full-width, 4 rows tall" with
  no warning). DEF-013 (closed 2026-07-22) proved the *actual* wire format
  (`gridsterCoords`) is **1-indexed** — "Every widget coordinate in the known-good corpus
  — 100+ widgets across `reference/references/` vendor MP exports plus every
  `knowledge/context/exports/*.json` capture — uses `x >= 1` and `y >= 1`; zero use 0 for
  either axis" — and that 0-based authoring is "a natural authoring mistake (0-based
  array-index thinking)" that caused a real production bug (inverted widget stacking on
  the shipped CPU Support Status dashboard). The fix is a defensive floor-clamp in the
  renderer, not a semantics change, and the DEF-013 closing entry explicitly recommends
  "authors should still prefer 1-based `coords` going forward to match the wire format
  directly." The still-open follow-up FB-017 exists specifically because the clamp is a
  backstop, not validation, and a fully-0-based layout can still render with a silent
  1-row widget overlap (per the framework-reviewer's own WARNING,
  `knowledge/context/reviews/framework/def013-gridster-floor-2026-07-22.md`). The
  authoring guide — the doc a future author reads *before* hitting the renderer — still
  teaches the exact pattern DEF-013 and FB-017 warn against, with a caption that reads as
  an endorsement ("full-width, 4 rows tall") rather than a caveat. → Update lines 320-329
  and the two worked examples to 1-based coords (`x: 1-12`, `y: 1-based, grows downward`),
  and consider a one-line callout citing DEF-013's floor-clamp as the safety net, not the
  spec. This is the highest-value finding this cycle — it is load-bearing precisely
  because it's read *before* authoring, unlike the defect registry which is read only
  after something breaks.
