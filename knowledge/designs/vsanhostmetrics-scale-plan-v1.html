vSAN Host Metrics at 70 clusters

A plan for porting the vsanhostmetrics pack to a native Java Tier 2 SDK adapter that holds up on one vCenter with 70 vSAN clusters, with answers to the concerns raised about collector memory, metric volume and trending.

2026-11-06 · from reading 1.4.7 and the open 2.0.0 PR, plus same-day measurements on a VCF Operations lab (8.18.7, 9.0.2, 9.1.1) and its 9.1.1 vCenter · VCF Content Factory

Port the design, not the code. The scaling problem is not the number of metrics defined. It is one Ops object per vSAN entity, which multiplies on hosts, NICs, disks, VMs and virtual disks, and one Performance Service call per entity type per cluster, run one after another.

The port fixes the first by owning no objects and stitching values onto vCenter's own HostSystem and VirtualMachine, which takes the pack from roughly 180,000 projected objects to zero. It fixes the second by running clusters in parallel. Whether one instance then carries 70 clusters depends on a throughput ceiling the lab cannot measure; the plan says so rather than assuming it. A line-for-line port that keeps today's model moves the problem into the collector JVM, where a failure takes every adapter on the proxy with it.

Where the numbers come from

What Ops charges for

Ops sizing is driven by objects first and metric series second, where a series is one metric key on one object, written once per cycle. Every object carries identity, relationships, a dynamic-threshold model per metric, a row in every list and a node in the relationship graph. A series on an existing object is cheap by comparison. The pack creates an object for everything it sees.

Three things people call "metrics": the 1,595 in the README are definitions in describe.xml and cost nothing until emitted; the counts on this page are series; each series writes one data point per cycle, 288 a day.

The sub-interval sample figure

The author's arithmetic, 2,200 metrics times 15 samples of 20 seconds per 5-minute window, sets the wrong design target twice.

  1. The vSAN Performance Service samples every 5 minutes, every minute with verbose mode on. Measured on the lab cluster: a 300-second interval, verbose off. The 20-second cadence belongs to vCenter's realtime PerformanceManager counters, which this pack never reads.
  2. Ops wants one value per metric per object per cycle. Adapters do not replay sub-interval samples. If a maximum over the interval matters for a particular metric, emit it as a second key for the few that matter.

What fails regardless of sizing is time. 2,310 serial calls at the measured 0.19-second median is about 7.3 minutes against a 5-minute cycle, before the pack's own inventory work, which on the lab cluster is most of the cycle: 6 to 11 seconds of calls inside a 28 to 75 second cycle.

Object model: own nothing, stitch

A host-scoped vSAN entity (DOM owner, DOM client, component manager, memory, CMMDS, RDT, zDOM, TCP/IP) is not an object. It is a metric group on the host. The vCenter adapter already models NICs this way: net:vmnic0|received_average is an instanced key on the HostSystem, not a vmnic object.

This is stitching, the pattern the factory already runs

Owning no host, VM or disk objects and pushing values onto vCenter's own resources through the Suite API is what the Content Factory calls ARIA_OPS stitching. The compliance adapter does it in production on 8.18.7, 9.0.2 and 9.1.1 with the buildkit's SuiteApiStitcher: batched pushes of about 100 resources per request, a resolver keyed on vCenter instance UUID plus MOID (never MOID alone), an Ops credential on the instance, failures logged and counted rather than thrown into the cycle. The port reuses that as is.

Stitched keys carry no label or unit, because a pak's describe.xml declares its own adapter kind, not VMWARE's. Compliance already names its keys for people for that reason; the port does the same, unit in the key name, group names settled before the first release.

Checked on devel 9.0.2 today, and not previously written down: instanced keys such as pNIC:vmnic0|… stitch and read back one per instance; a pushed value may be older than the newest stored sample; both push endpoints return 200 and the value becomes readable anywhere from under a minute to over three minutes later, so landing checks are reads. Pushed stats are attributed to the Suite API's own adapter, not to the pak's instance, so the pak's Ops self-metric will not count them; the pak logs its own per-cycle counts and the push results instead. How the Metrics tab draws a stitched instanced key is unverified. Build 1 proves the stitch on 8.18, 9.0 and 9.1, not only on 9.0.2.

The identity map is the one hard piece, and the pack already has it: vSAN node uuid to host MOID through vCenter (the fix for the 1.4.x hostname-join bug), vdisk uuid to VM, disk uuid to host. The API probe confirmed the node-uuid and VM instanceUuid joins on the lab. Build it once per cluster, cache it, refresh every few cycles, and use it to address pushes.

Collector: what the API allows, measured

Current loop: for each cluster, for each entity type, one VsanPerfQueryPerf call with one wildcard spec, serial, 15-minute window. The lab vCenter (9.1.1, one ESA cluster, 5 hosts, 30 VMs) was probed read-only to find out what can change; the full map is in the factory under knowledge/context/api-maps/vsan-performance-service.md.

What that means at 70 clusters

The call floor is 2,310 per cycle, about 1,900 once each cluster skips the types it is known not to have. Serial at the 0.19 s median is about 7.3 minutes, which fails the 5-minute cycle. At the measured 7 calls/s ceiling it is about 5.5 minutes, marginal. If the ceiling is per cluster rather than per vCenter, an 8-worker pool across clusters gets close to a minute. That one measurement decides whether one instance can carry 70 clusters or whether sharding is mandatory.

The pack's full cycle on the lab cluster takes 28 to 75 s on average while the 33 calls take 6 to 11 s. Most of the cycle is inventory walking, name resolution and relationship re-attachment, not the Performance Service. The zero-objects model removes the re-attach work entirely, and the name map can be cached across cycles.

  1. Parallelise across clusters with a bounded pool.One wildcard call per type is the floor, so the only lever on wall time is running clusters side by side. Size the pool to the measured ceiling, not the cluster count, and bound it: an unbounded pool is exactly what takes a collector down.
  2. Learn per cluster which types fault or come back empty.Probe once, skip from then on, re-probe daily. On the lab cluster that is 6 of 33 calls saved per cycle.
  3. Send the label list on every spec.Half the bytes to parse and hold; the in-scope list already exists in the pack.
  4. 7-minute window.Guarantees one 5-minute bucket; 5 minutes drops entities at the boundary.
  5. Process one cluster's responses and discard them before the next.Memory then scales with the largest cluster and the pool size, not the vCenter.
  6. One vCenter session per instance, reused across cycles.Re-login once on NotAuthenticated, since the idle timeout is unmeasured.
  7. Cache the inventory.Host, VM and vdisk name maps and the hardware properties change rarely; rebuild every N cycles, not every cycle.
  8. Shard by cluster across instances.A cluster filter parameter (names or regex) lets the 70-cluster environment run several instances on several Cloud Proxies. Same credential, same pak. If the ceiling is per vCenter this is the scale-out; if per cluster, it is still the fault-isolation story.

JVM and memory: what the port inherits by moving into the collector

The author's two concerns, that 2,200 more metrics inside the collector JVM raise scaling issues and that a crash takes the collector with it, are both right. They do not argue against the port; they set its design constraints. A Java adapter shares the collector's heap and threads with every other adapter on that collector, so the port is built to a budget from the first commit.

What is actually in the heap

2,200 metric definitions cost nothing at runtime; describe.xml is parsed once. The heap during a cycle is dominated by three things, none of them the definition count. The sizes below are measured for one 5-host cluster; the multiples are inferred.

  • Parsed responses. One cluster's full cycle is 109 KB on the wire and 1.3 MB decoded as XML or about 2.5 MB pretty-printed as JSON, 0.7 MB with the label filter. Object trees built from that are several times larger again. Hold 70 clusters' responses at once and that is tens to a few hundred megabytes on a heap that has about 65 to spare.
  • The result object. Every series emitted in a cycle sits in memory until it is pushed. Zero own objects and batched pushes shrink this to the batch in flight.
  • Threads. Each parallel cluster call holds its response. Parallelism × per-cluster response is the high-water mark, which is why the pool is bounded and sized to the budget, not the cluster count.
  • The collector is not empty. The lab's devel 9.0.2 analytics node shows hundreds of full GCs and one 7-second pause with 12 adapter instances on a 1 GB collector heap. A port that adds a few hundred megabytes of transient response trees per cycle to that JVM is the crash the author is worried about.

What changes when the code moves from a container into the collector

The mitigation is the design in the two sections above: bounded parallelism, per-cluster process-and-discard, a short window, no retained result, and no objects of its own. A Java port that keeps one object per entity and one call per type ships today's problem into the collector JVM, where a failure has a blast radius.

Rules for the port

  • Port the Performance Service client first, with its tests. The Python pack isolates everything that can be wrong about the data in one module with no SDK imports and 26 offline tests. Port that module to a plain Java class with the same tests before touching the adapter lifecycle. The entityRefId parser, the name map and the last-sample-in-window logic are where the data bugs live.
  • Use the JSON transport, no vSAN SDK jars. Measured on the 9.1.1 lab vCenter: POST /sdk/vim25/{release}/vsan/VsanPerformanceManager/vsan-performance-manager/VsanPerfQueryPerf reaches the same vsan-health handlers as SOAP with the same limits, fault keys and ~7 calls/s ceiling, and the 33-call cycle ran slightly faster (4.6 to 5.0 s against 5.3 to 7.7 s). Java's HttpClient plus Jackson and four small classes replace the vSAN bindings. Details that bit during the probe: every spec needs "_typeName":"VsanPerfQuerySpec"; dates are ISO strings in UTC and a non-UTC offset is silently dropped; read the release id from /sdk/vimServiceVersions.xml; the session token comes back in the vmware-api-session-id header; send Accept-Encoding: gzip or one type comes back 17× larger; the values CSV contains literal None tokens; re-login on NotAuthenticated. One caveat: this was measured on a 9.1.1 server only. That server accepts release ids 8.0.3.0 and up, but whether an 8.0 U3 vCenter serves the endpoint is untested, and the target environment's vCenter version has to be checked before the transport choice is final.
  • The heap budget is about 65 MB per instance. Measured on the lab's devel 9.0.2 collector: the JVM runs with a 1 GB maximum, holds about 230 to 306 MB live at steady state with 12 adapter instances, and reached 682 MB against a 683 MB old-gen cap during a pressure period in September. A tenth of the roughly 650 MB of headroom is an honest claim, and the replay harness has to show the largest cluster's parsed response × the pool size under it. The lab's Cloud Proxies, where a customer would actually run this, could not be read yet and are probably smaller and more crowded.
  • Stream and discard per cluster. Never build a list of all responses.
  • One vCenter session per adapter instance, reused across cycles, re-logged on expiry. Seventy logins per cycle is a vCenter load problem and a token-churn problem.
  • Every outbound call carries a timeout, and the collect cycle has a deadline below the collection interval. A stuck HTTP call must never hold a collector thread into the next cycle.
  • Ship the pak with a recommendation to pin the instance to its own collector group. That is an install-time control a customer can apply on day one, and it gives them a per-pack memory reading.
  • A distinct adapter kind key, installed side by side with the Python pack. There is no in-place container-to-Java upgrade on 9.0.2: a same-identity pak reports success and leaves the container adapter live. Existing 2.0.0 users uninstall, install, and recreate instances and credentials.
  • The support posture is still build-and-figure-it-out: the Ops jars are stubbed by hand and the Java SDK is not Broadcom's documented path. The Content Factory's sdk-template repo, buildkit and CI already carry that cost; start from them rather than from scratch.

Metric scope: three levers instead of one switch

Keep the current principle, every metric declared and scope decides what is emitted. That is already right; a declared metric nobody emits costs nothing. Replace the dashboard/all enum with:

  1. Tiers: cluster, host, disk, vm, cumulative. Default host. VM is the tier that multiplies by thousands and is opt-in per instance. With the cluster filter, a site turns VM detail on for the two clusters it is troubleshooting.
  2. Exclude list: free text, kinds or metric groups to drop on top of the tier, so a site trims without waiting on a release.
  3. Cadence: collect VM-tier kinds every Nth cycle. N = 3 gives 15-minute VM trends. The window logic already takes the last sample in the window, so gaps are tolerated.

And measure it: log per cycle the objects touched, the series pushed per group, the per-cluster and per-type call time and the push batch results. The adapter instance's own Ops self-metric does not see stitched series, so the log is the number. The README's "11 to 16 seconds" says nothing about ingest.

Content: trending comes free once metrics live on the host

The author's complaint is that views are fixed to a time period, sparklines and health scores do not scale, and clicking a cell in a view does not reach the metric's trend. That is a consequence of the object model, not a limit of Ops. Once DOM owner latency is a key on the HostSystem:

  • The host's Metrics tab trends it with the normal time slider, next to vCenter's CPU, memory and network keys. HostSystem carries no vSAN keys of its own today. No hunt.
  • A dashboard is Object List of hosts in the cluster, then Metric Chart, with the standard selection interaction. Click a host, see the chart. That is the vCenter adapter's own dashboard pattern.
  • Scoreboards follow dashboard time (the pack's own BACKLOG established the dashboardTime period setting), and a scoreboard of eight hosts × four metrics with sparklines is a normal widget load.
  • Symptoms and alerts attach to HostSystem, so an alert on DOM owner write latency shows up where every other host alert does, in the same policy. Health scores are not needed.

The shipped list views remain useful as tabular drill-down; they stop being the only path.

Other things worth knowing before the rewrite

vCenter is the other side of the scale problem

The Performance Service runs inside vCenter's vsan-health process, with its own heap, and the ~7 calls/s ceiling was identical over SOAP and JSON, so it lives there. The built-in vSAN adapter already queries it every cycle for every cluster; this pack doubles that. Skipping known-empty types and sending the label filter is a courtesy to vCenter as much as to the collector.

Verbose mode changes the payload

A cluster with Performance Service verbose mode on returns 1-minute points, five times the rows for the same window. The 7-minute window matters most there. The adapter must not depend on which mode a cluster is in.

One session, not seventy

Log in once per instance and hold the session across cycles, re-logging in once on NotAuthenticated. A login per cluster per cycle is 20,000 tokens a day and is the first thing a vCenter admin will see in the logs.

Relationship writes are the sharp edge

The pack's own notes record a day when attaching to vCenter objects wiped every child under each host. The SDK serialises relationships parent-centric and treats what you send as the complete set. With zero new objects there is nothing to attach, and that whole class of defect goes away.

Dynamic thresholds cost per series

Ops builds a dynamic-threshold model for every series that has data, nightly. 1.36 million series is 1.36 million models. The tiers and the cadence lever are what keep this reasonable; it is another reason the VM tier should be opt-in.

Metric key stability

Once keys live on HostSystem they are part of customers' views, symptoms and super metrics. Settle the group naming before the first release, and treat a renamed key the way the pack already treats a removed kind: a breaking version with a migration note.

Airgap is the real win of the port

A Java pak is one file with no image to pull. For the customers who cannot or will not approve a registry proxy, that is the reason to do this at all, and it is a better reason than memory.

Collector placement is a control the customer already has

An adapter instance can be pinned to a collector group. Putting this pack on its own Cloud Proxy, or its own group of proxies when sharded, contains a bad cycle to this pack and gives the customer a per-pack memory and CPU reading they do not otherwise get.

Scale-testing without 70 clusters

The author cannot scale-test. He does not need 70 clusters.

  1. Record one cluster's Performance Service responses for every entity type, one cycle, as raw JSON. The API map describes the recording procedure.
  2. Replay them through a fake client that answers VsanPerfQueryPerf from the recording, with cluster, host, VM and vdisk uuids rewritten per synthetic cluster. 70 synthetic clusters from one recording.
  3. Run the collect path against it from a plain JUnit test and measure wall time, peak heap, and series pushed per cycle. That is the number the customer will ask for, and it runs in CI on every change.

The offline split the Python pack already has, with the Performance Service client carrying no SDK imports, is the shape to keep in Java: the same tests, the same recording, no collector needed. What a replay cannot answer is the vsan-health throughput ceiling; that needs the simulator to model the service, or a real multi-cluster vCenter.

Order of work

  1. Record and measure on the Python pack.Capture one cluster's responses, add per-kind logging. That recording is the Java port's test fixture and the before number.
  2. Port the Performance Service client to Java with its tests.Parser, name map, last-sample logic, replay harness at 70 synthetic clusters. No adapter lifecycle yet.
  3. Collector loop.Parallel clusters on a bounded pool, learned types per cluster, labels, 7-minute window, cluster filter parameter, timeouts and a cycle deadline. Prove heap and wall time against the harness.
  4. Model.Stitch host-scoped kinds onto HostSystem, DOM owner first, prove on all three lab instances, then the rest. VM-scoped kinds last, behind the vm tier. Disk tier per the lab findings.
  5. Content.Rebuild the dashboards host-centric: Object List, Metric Chart, Scoreboard. Views stay.
  6. Scope.Tiers, exclude list, cadence.

The open 2.0.0 pull request on the Python pack (certificate handling, surfaced collection errors, per-cluster isolation, username in the credential) is still worth landing: it keeps the shipping pack honest while the port is built, and its per-cluster isolation and credential shape are the behaviour the Java port matches from day one.

Decisions, 2026-11-06

  • Vehicle: a native Java Tier 2 adapter in a VCF Content Factory SDK repo, instantiated from the factory's sdk-template and registered alongside the other managed paks, not a branch of the upstream repo. The upstream author reviews; the Python fork keeps shipping meanwhile.
  • Build 1, the MVP: one cluster, host tier only, three groups stitched onto the VMWARE HostSystem: DOM owner, DOM client, pNIC. No VM or disk tier. It proves the stitch on 8.18, 9.0 and 9.1, the identity map and the heap budget.
  • Build 2: metric parity with the Python pack's default scope, 451 keys, on the zero-objects model; the cluster-object question is settled there.
  • Throughput ceiling: settled when a simulator or a multi-cluster vCenter is available. Until then the adapter carries an advanced instance setting for performance-timing debug logging, off by default: per-cluster and per-type call time and bytes, pool occupancy, cycle total, push batch timings.
  • Still open: Cloud Proxy collector heap (needs an SSH credential), UI rendering of stitched instanced keys (build 1 shows it), Suite API ingest at build 2 volume, and the target vCenter's version for the JSON transport.
