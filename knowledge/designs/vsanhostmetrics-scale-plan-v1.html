vSAN Host Metrics at 70 clusters

A plan for porting the vsanhostmetrics pack to a native Java Tier 2 SDK adapter that holds up on one vCenter with 70 vSAN clusters, with answers to the concerns raised about collector memory, metric volume and trending.

2026-11-06 · from reading 1.4.7, the open 2.0.0 PR and a recon of a VCF Ops 9.0.2 lab · VCF Content Factory

Port the design, not the code. The scaling problem is not the number of metrics defined. It is one Ops object per vSAN entity, which multiplies on hosts, NICs, disks, VMs and virtual disks, and one Performance Service call per entity type per cluster, run one after another.

A Java port that fixes those two is a good fit for the collector: the Performance Manager answers over plain HTTP and JSON on 8.0.3 and later, so the port needs no vSAN SDK jars, and the Java SDK's Suite API push is the natural way to land metrics on vCenter's own objects, and that is the move that takes the pack from ~110,000 objects to zero. A line-for-line port that keeps today's model moves the problem into the collector JVM, where a failure takes every adapter on the proxy with it.

Where the numbers come from

What Ops charges for

Ops sizing is driven by objects first and metric series second, where a series is one metric key on one object, written once per cycle. Every object carries identity, relationships, a dynamic-threshold model per metric, a row in every list and a node in the relationship graph. A metric on an existing object is cheap by comparison. The pack currently creates an object for everything it sees.

The 20-second sample figure

"2200 metrics at 20 second intervals in a 5 minute window is 33k per 4 node cluster"

Two corrections, because this sets the wrong design target.

  1. The vSAN Performance Service samples every 5 minutes, every 1 minute with verbose mode on. The 20-second cadence belongs to vCenter's realtime PerformanceManager counters, which this pack never reads. The pack already pulls a 15-minute window and keeps the last sample.
  2. Ops wants one value per metric per object per cycle. Adapters do not replay sub-interval samples. The vCenter adapter averages its 20-second realtime points into one 5-minute value. If a maximum over the interval matters for a particular metric, emit it as a second metric such as latencyRead|max, computed in the adapter, for the few that matter.

So per-cycle load is objects × metrics, once. Nothing is 15×.

Three numbers that Ops people all call "metrics": the 1,595 in the README are definitions in describe.xml and cost nothing until emitted; the ~900,000 above are series, one per metric key per object, which is what sizing tables and dynamic-threshold models count; and each series writes one data point per cycle, about 260 million a day at 288 cycles.

Against Broadcom's 8.18 sizing guideline, the metric count is not the problem: 900,000 series fit a Small Cloud Proxy (1.2 million) and a Small analytics node (1.6 million). The object count is a real budget line: 110,000 objects needs an Extra Large node (100,000 single-node) or a Medium cluster (136,000), sharded across three Standard Cloud Proxies at 40,000 each. Deployable, but the pack would be adding about six objects per VM to a deployment where the vCenter adapter already carries three or four, roughly doubling the customer's object count for one pack.

What actually breaks is time. 2,310 serial calls at the lab's 0.4 s each is about 15 minutes against a 5-minute cycle, so a collection never finishes before the next one starts. With the VM tier off, the model is 8,800 objects and 160,000 series, inside a Small Cloud Proxy, and the time problem is unchanged.

Object model: stop creating objects

A host-scoped vSAN entity (DOM owner, DOM client, component manager, LSOM, memory, CMMDS, RDT, zDOM, TCP/IP) is not an object. It is a metric group on the host. Ops already models exactly this: the vCenter adapter puts net:vmnic0|received_average on the HostSystem as an instanced metric, not as a vmnic object. The pack should do the same.

Result: zero new objects from this pack at the host, disk and VM layers. The 70-cluster customer goes from ~110,000 objects to 0, or 70 if a cluster object is kept as a landing spot for cluster dashboards. The "9 tree structures" disappear; the tree is vCenter's.

Metrics per cycle do not change by this move alone, which is why scope still matters below. But 900,000 metrics on existing objects is a sizing line item; 110,000 objects is a redesign of the customer's Ops deployment.

This is stitching, the pattern the factory already runs

Owning no host, VM or disk objects and pushing values onto vCenter's own resources through the Suite API is what the Content Factory calls ARIA_OPS stitching. The compliance adapter does it in production on 8.18.7, 9.0.2 and 9.1.1 with the buildkit's SuiteApiStitcher: batched pushes of about 100 resources per request, a resolver keyed on vCenter instance UUID plus MOID (never MOID alone), an Ops credential on the instance, failures logged and counted rather than thrown into the cycle. The port reuses that as is.

Stitched keys carry no label or unit, because a pak's describe.xml declares its own adapter kind, not VMWARE's. Compliance already names its keys for people for that reason; the port does the same, unit in the key name, group names settled before the first release.

Checked today on devel and not previously written down: instanced keys such as pNIC:vmnic0|… stitch and read back one per instance; a pushed value may be older than the newest stored sample; the push returns 200 one to four minutes before the value is readable, so landing checks are reads, not response codes.

The identity map is the one hard piece, and the pack already has it: vSAN node uuid to host MOID through vCenter (the fix for the 1.4.x hostname-join bug), vdisk uuid to VM, disk uuid to host. Build it once per cycle per cluster and use it to address pushes instead of to add children.

Collector: what the API allows, measured

Current loop: for each cluster, for each entity type, one VsanPerfQueryPerf call with one wildcard spec, serial, 15-minute window. At 70 clusters that is 2,310 calls per cycle. What that means at 70 clusters

The call floor is 2,310 per cycle, about 1,900 once each cluster skips the types it is known not to have. Serial at 0.19 s per call is 6 to 7.5 minutes, which fails the 5-minute cycle. At the measured 7 calls/s ceiling it is 4.5 to 5.5 minutes, marginal. If the ceiling is per cluster rather than per vCenter, an 8-worker pool across clusters gets close to a minute. That one measurement on a multi-cluster vCenter decides whether one instance can carry 70 clusters or whether sharding is mandatory.

One more finding from the live footprint: the pack's full cycle on this same cluster takes 28 to 75 s, while the 33 perf queries take 6 to 11 s. Most of the cycle is inventory walking, name resolution and relationship re-attachment, not the Performance Service. The zero-objects model removes the re-attach work entirely, and the name map can be cached across cycles and refreshed every few.

  1. Parallelise across clusters with a bounded pool.One wildcard call per type is the floor, so the only lever on wall time is running clusters side by side. Size the pool to the measured ceiling, not the cluster count, and bound it: an unbounded pool is exactly what takes a collector down.
  2. Learn per cluster which types fault or come back empty.Probe once, skip from then on, re-probe daily. On the lab cluster that is 6 of 33 calls saved per cycle.
  3. Send the label list on every spec.Half the bytes to parse and hold, and the in-scope list already exists in the pack.
  4. 7-minute window.Guarantees one 5-minute bucket; 5 minutes drops entities at the boundary.
  5. Process one cluster's responses and discard them before the next.Memory then scales with the largest cluster and the pool size, not the vCenter.
  6. One vCenter session per instance, reused across cycles.Re-login on expiry only.
  7. Cache the inventory.Host, VM and vdisk name maps and the hardware properties change rarely; rebuild every N cycles or on a known inventory event, not every cycle.
  8. Shard by cluster across instances.A cluster filter parameter (names or regex) lets the 70-cluster customer run several instances on several Cloud Proxies. Same credential, same pak. If the throughput ceiling is per vCenter, this is the scale-out; if it is per cluster, it is still the fault-isolation story.

JVM and memory: what the port inherits by moving into the collector

"when you collect 2200 more metrics within the existing jvm's runtime it brings up scaling issues … and if it crashes it'll crash the collector"

Both halves are true. They do not argue against the port; they set its design constraints. A Java adapter shares the collector's heap and threads with every other adapter on that Cloud Proxy, so the port has to be built to a budget from the first commit, not tuned afterwards.

What is actually in the heap

2,200 metric definitions cost nothing at runtime; describe.xml is parsed once. The heap during a cycle is dominated by three things, none of them the metric count:

  • Parsed SOAP responses. A JAX-WS or pyVmomi object tree is 5 to 10× its wire size. One cluster's full entity set is a few megabytes on the wire and tens of megabytes as objects. Hold 70 of them at once and that is the whole budget.
  • The result object. Every object and metric emitted in a cycle sits in memory until the SDK serialises it. 110,000 objects × their metrics is hundreds of megabytes of result before any JSON is written. Zero new objects and batched pushes shrink this to the batch in flight.
  • Threads. Each parallel cluster query holds its response. Parallelism × per-cluster response is the high-water mark, which is why the pool must be bounded and sized to the memory limit, not to the cluster count.
  • The collector is not empty. The lab's 9.0.2 analytics node already shows hundreds of full GCs and one 7-second pause with 12 adapter instances on a 1 GB collector heap. A port that adds a few hundred megabytes of transient SOAP trees per cycle to that JVM is the crash the author is worried about.

What changes when the code moves from a container into the collector

The mitigation is the design in the two sections above: bounded parallelism, per-cluster process-and-discard, a short window, no retained result, and no objects of its own. A Java port that keeps one object per entity and one call per type ships today's problem into the collector JVM, where a failure has a blast radius.

Rules for the port

  • Port the Performance Service client first, with its tests. The Python pack already isolates everything that can be wrong about the data in one module with no SDK imports and 26 offline tests. Port that module to a plain Java class with the same tests before touching the adapter lifecycle. The entityRefId parser, the name map and the last-sample-in-window logic are where the data bugs live.
  • Use the JSON transport, no vSAN SDK jars. Measured 2026-11-06 on the 9.1.1 lab vCenter: POST /sdk/vim25/{release}/vsan/VsanPerformanceManager/vsan-performance-manager/VsanPerfQueryPerf reaches the same vsan-health handlers as SOAP with the same limits, the same fault keys and the same ~7 calls/s ceiling, and the 33-call cycle ran slightly faster (4.6 to 5.0 s against 5.3 to 7.7 s). Java's HttpClient plus Jackson and four small classes replace the vSAN bindings. Details that bit during the probe: every spec needs "_typeName":"VsanPerfQuerySpec"; dates are ISO strings in UTC, a non-UTC offset is silently dropped; release ids 8.0.3.0, 9.0.0.0 and 9.1.1.0 work and older ones fault, so read it from /sdk/vimServiceVersions.xml; the session token comes back in the vmware-api-session-id header; send Accept-Encoding: gzip or one type comes back 17× larger; the values CSV contains literal None tokens; re-login on NotAuthenticated since the idle timeout is not discoverable.
  • The heap budget is about 100 MB, not 300. Measured on the lab's devel 9.0.2 collector: the JVM runs with a 1 GB maximum, holds 230 to 240 MB live after a full GC with 12 adapter instances, peaked at 371 MB over the last eight days and at 682 MB in September against a 683 MB old-gen cap. Against the eight-day peak about 650 MB is free; a new instance that claims a tenth of that is honest, and the replay harness has to show the largest cluster's parsed response × the pool size under it. The lab's Cloud Proxies could not be read yet and are probably smaller and more crowded.
  • Stream and discard per cluster. Never build a list of all responses.
  • One vCenter session per adapter instance, reused across clusters and cycles, re-logged on expiry. Seventy logins per cycle is a vCenter load problem and a token-churn problem.
  • Every outbound call carries a timeout, and the collect cycle has a deadline below the collection interval. A stuck SOAP call must never hold a collector thread into the next cycle.
  • Ship the pak with a recommendation to pin the instance to its own collector group. That is an install-time control a customer can apply on day one, and it gives them a per-pack memory reading.
  • The support posture is still build-and-figure-it-out: the Ops jars are stubbed by hand and the Java SDK is not Broadcom's documented path. The Content Factory's sdk-template repo, buildkit and CI already carry that cost; start from them rather than from scratch.

Metric scope: three levers instead of one switch

Keep the current principle, every metric declared and scope decides what is emitted. That is already right; a declared metric nobody emits costs nothing. Replace the dashboard/all enum with:

  1. Tiers: cluster, host, disk, vm, cumulative. Default host. VM is the tier that multiplies by thousands and is opt-in per instance. With the cluster filter, a site turns VM detail on for the two clusters it is troubleshooting.
  2. Exclude list: free text, kinds or metric groups to drop on top of the tier, so a site trims without waiting on a release.
  3. Cadence: collect VM-tier kinds every Nth cycle. N = 3 gives 15-minute VM trends. The window logic already takes the last sample in the window, so gaps are tolerated.

And measure it: log per cycle the objects touched and metrics emitted per kind and the per-cluster query time, and point users at the adapter instance's own metrics-collected self-metric. The README's "11 to 16 seconds" says nothing about ingest.

Content: trending comes free once metrics live on the host

"views are time period fixed. sparklines aren't really scalable, neither are health scores. so when you click the metric you have to hunt to get from the view to the actual metric trending"

This is a consequence of the object model, not a limit of Ops. Once DOM owner latency is a metric on the HostSystem:

  • The host's Metrics tab trends it with the normal time slider, next to CPU, memory and vCenter's own vSAN metrics. No hunt.
  • A dashboard is Object List of hosts in the cluster, then Metric Chart, with the standard selection interaction. Click a host, see the chart. That is the vCenter adapter's own dashboard pattern.
  • Scoreboards follow dashboard time (the pack's own BACKLOG established the dashboardTime period setting), and a scoreboard of eight hosts × four metrics with sparklines is a normal widget load.
  • Symptoms and alerts attach to HostSystem, so an alert on DOM owner write latency shows up where every other host alert does, in the same policy. Health scores are not needed.

The shipped list views remain useful as tabular drill-down; they stop being the only path.

The pack adds five times the vCenter adapter's object count and about three quarters of its metric volume for one small cluster. The collection time matters most: one cluster takes 28 s on average on 9.0.2 and 75 s on 8.18.7. Seventy clusters in series at those rates is 33 to 87 minutes per 5-minute cycle, which is why batching and parallelism are step one. Container memory sits near 90 MB against the 1 GB limit and CPU near 2%, so the per-cluster footprint is small; it is the serial loop, not the resource use, that fails to scale.

  • The pack's core is not duplicated. The built-in vSAN adapter exposes nothing for DOM owner, DOM client, component manager, RDT, zDOM, pNIC, vmknic, TCP/IP, CMMDS or per-VM vSAN. Those layers are the pack's reason to exist. The plan only moves where they land.
  • The disk tier is largely duplicated. Built-in vSAN|Performance|* on the ESA disk object covers 8 of 8 cache-disk, 8 of 13 capacity-disk and 4 of 5 ESA disk-layer metrics by name. Drop the disk tier from the default scope, or stitch the leftovers onto the built-in disk object, whose VSANID equals the pack's disk uuid.
  • Cluster stitching has a key. The built-in cluster ID is vSAN Cluster(domain-cNNNN, datacenter); parse the MoRef and match the VMWARE cluster on its object id plus vCenter id. Cluster-level DOM metrics overlap the built-in 11 performance keys only by name: the built-in is one aggregate, the pack is per layer. Keep the pack's.
  • Host stitching needs no new key. The pack already resolves vSAN node uuid to host MOID through vCenter.

Still open: whether to keep one own-kind cluster object per vSAN cluster as a landing spot for cluster dashboards, or to push cluster metrics onto the built-in vSAN Cluster object and own nothing. Seventy objects either way; the question is which object customers already navigate to.

Other things worth knowing before the rewrite

vCenter is the other side of the scale problem

The Performance Service runs inside vCenter's vsan-health process, with its own heap. The built-in vSAN adapter already queries it every cycle for every cluster; this pack doubles that. 70 clusters × 33 types × every 5 minutes is a load the customer's vCenter will notice, and a slow vsan-health answers slowly for the built-in adapter too. Batching per cluster and skipping unsupported types is a courtesy to vCenter as much as to the collector.

Verbose mode changes the payload

A cluster with Performance Service verbose mode on returns 1-minute points, five times the rows for the same window. The window shrink to 7 minutes matters most there. The adapter should not depend on which mode a cluster is in.

One session, not seventy

Log in to vCenter once per cycle, or hold the session across cycles and re-login on expiry. A login per cluster per cycle is 20,000 SSO tokens a day and is the first thing a vCenter admin will see in the logs.

Relationship writes are the sharp edge

The pack's own notes record a day when attaching to vCenter objects wiped every child under each host. The SDK serialises relationships parent-centric and treats what you send as the complete set. With zero new objects there is nothing to attach, and that whole class of defect goes away. That is a quiet but real benefit of the object-model change.

Dynamic thresholds cost per metric

Ops builds a dynamic-threshold model for every metric that has data, nightly. 900,000 metrics is 900,000 models. The tiers and the cadence lever are what keep this reasonable; it is another reason the VM tier should be opt-in.

Metric key stability

Once metrics live on HostSystem, their keys become part of customers' views, symptoms and super metrics. Settle the group naming before the first release of the new model, and treat a renamed key the way the pack already treats a removed kind: a breaking version with a migration note.

Airgap is the real win of the port

A Java pak is one file with no image to pull. For the customers who cannot or will not approve a registry proxy, that is the reason to do this at all, and it is a better reason than memory.

Collector placement is a control the customer already has

An adapter instance can be pinned to a collector group. Putting this pack on its own Cloud Proxy, or its own group of proxies when sharded, contains a bad cycle to this pack and gives the customer a per-pack memory and CPU reading they do not otherwise get.

Scale-testing without 70 clusters

The author cannot scale-test. He does not need 70 clusters.

  1. Record one cluster's Performance Service responses for every entity type, one cycle, raw SOAP or the pyVmomi objects pickled.
  2. Replay them through a fake perf object that answers VsanPerfQueryPerf from the recording, with cluster, host, VM and vdisk uuids rewritten per synthetic cluster. 70 synthetic clusters from one recording.
  3. Run the collect path against it from a plain JUnit test and measure wall time, peak heap, and objects and metrics pushed per cycle. That is the number the customer will ask for, and it runs in CI on every change.

The offline split the Python pack already has, with the Performance Service client carrying no SDK imports, is the shape to keep in Java: the same tests, the same recording, no collector needed.

Order of work

  1. Record and measure on the Python pack.Capture one cluster's responses, add per-kind logging. That recording is the Java port's test fixture and the before number.
  2. Port the Performance Service client to Java with its tests.Parser, name map, last-sample logic, replay harness at 70 synthetic clusters. No adapter lifecycle yet.
  3. Collector loop.Batch per cluster, bounded pool, 7-minute window, learn unsupported types, cluster filter parameter, timeouts and a cycle deadline. Prove heap and wall time against the harness.
  4. Model.Suite API push of host-scoped kinds onto HostSystem, one kind first (DOM owner, the 38-metric one), prove on the lab for a day, then the rest. VM-scoped kinds last, behind the vm tier. Drop or stitch the disk tier per the lab findings.
  5. Content.Rebuild the dashboards host-centric: Object List, Metric Chart, Scoreboard. Views stay.
  6. Scope.Tiers, exclude list, cadence.

The open 2.0.0 pull request on the Python pack (certificate handling, surfaced collection errors, per-cluster isolation, username in the credential) is still worth landing: it keeps the shipping pack honest while the port is built, and its per-cluster isolation and credential shape are the behaviour the Java port should match from day one.

Decisions, 2026-11-06

  • Vehicle: a native Java Tier 2 adapter in a VCF Content Factory SDK repo, instantiated from the factory's sdk-template. The upstream author reviews; the Python pack keeps shipping meanwhile.
  • Build 1, the MVP: one cluster, host tier only, three groups pushed onto the VMWARE HostSystem: DOM owner, DOM client, pNIC. No VM or disk tier. It proves the push, the identity map and the heap budget.
  • Build 2: metric parity with the Python pack's default scope, 451 keys, on the zero-objects model.
  • Throughput ceiling: settled when a simulator or a multi-cluster vCenter is available. Until then the adapter carries an advanced instance setting for performance-timing debug logging, off by default: per-cluster and per-type call time and bytes, pool occupancy, cycle total, push batch timings.
  • In flight: JSON transport for the Performance Manager on 9.1, collector JVM heap on the lab Cloud Proxies, and an instanced-key push test onto a devel host.
